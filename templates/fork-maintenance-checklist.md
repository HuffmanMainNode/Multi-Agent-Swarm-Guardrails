# Responsible Fork Maintenance Checklist

Use this when forking an existing project for a contribution, experiment, or maintained derivative.

## Before forking

- [ ] I read the upstream README, license, contribution guide, and security policy.
- [ ] I understand why a fork is better than a bookmark, clone, or branch.
- [ ] I checked whether an existing issue or pull request already addresses my goal.
- [ ] I know whether the upstream repository is public or private and what its license permits.
- [ ] I will not copy private material or secrets.

## Set up

- [ ] I forked the correct upstream repository.
- [ ] I cloned my own fork, not a similarly named repository.
- [ ] I added the original repository as the upstream remote.
- [ ] I confirmed origin points to my fork and upstream points to the original.
- [ ] I created a focused branch for this contribution.

## Work

- [ ] The change has one clear purpose.
- [ ] I preserved license notices and attribution.
- [ ] I did not add credentials, private data, or generated clutter.
- [ ] I added tests or explained why tests are not applicable.
- [ ] I reviewed the complete diff.
- [ ] I checked whether upstream changed before proposing the contribution.

## Pull request

- [ ] The PR targets the intended upstream repository and branch.
- [ ] The description explains the problem, approach, tests, and limitations.
- [ ] I searched for duplicate work.
- [ ] I am not splitting trivial changes or posting duplicate PRs to inflate activity.
- [ ] I will respond constructively to review.

## Afterward

- [ ] I know whether the fork remains useful.
- [ ] If maintaining a derivative, I document differences and upstream tracking.
- [ ] If the fork is no longer needed, I check for open work and dependencies before deleting it.
- [ ] I keep a separate backup for important work.

A fork count is not a measure of contribution quality. Keep forks that serve a real purpose.
